# U4Claude v1.9.5

One fix: the usage circle is back for plans that no longer have a 5-hour limit.

## What changed

- **The circle shows your 7-day limit when your plan has no 5-hour window.** Anthropic removed the 5-hour limit from the top subscription, and the API stopped returning that window entirely. The popover's main circle is the 5-hour reading by default, so with nothing behind it the circle and its percentage simply disappeared — even though the 7-day number and the weekly per-model numbers were arriving normally. The app now notices the 5-hour limit isn't there, drops its row, and promotes the 7-day limit to the main circle.

If your plan still has a 5-hour limit, nothing changes.

## Internal

- Two display-layer assumptions, both now corrected.
- `UserSettings.getActiveDisplayTypes` appended `.fiveHour` and `.sevenDay` unconditionally in smart mode, on the stated reasoning that "every Claude account is subject to both limits" (backported from upstream `fffff55`). That is no longer true. Smart mode now lists each of the two only when the account actually has it — consistent with how that branch already treated every other limit type. `sevenDay` is unaffected in practice: `toUsageData()` returns a non-optional `LimitData`, emitting a 0% placeholder when the field is missing, so brand-new accounts still show the row from day one and the active list is never empty in smart mode.
- `getPrimaryLimitData` and `colorForPrimaryByActiveTypes` chained their 5-hour and 7-day cases with `else if`. With `.fiveHour` active but empty, control fell past the 7-day case to `return nil` / `.gray`, so an account with a perfectly usable 7-day limit still got no ring. Both now test the two independently and fall back. This also keeps custom mode correct: a user who explicitly selected a limit that has no data still gets the 0% placeholder rather than an empty popover.
  - **Correction (added in v1.9.6):** the custom-mode sentence above is wrong. 7-day data is always present, so the placeholder branch never ran, and custom mode with 5-hour and 7-day both ticked drew the 7-day limit as both rings. Fixed in [v1.9.6](v1.9.6.md).
- The 5-hour row's absence is now genuine rather than a row reading "-", and the thin outer ring is correctly not drawn, since it already required both types to be active. The menu bar icon needed no change — `MenuBarIconRenderer` already fell back to the 7-day percentage, which is why only the popover circle broke.
- v1.9.3's optional `five_hour` is what kept data flowing at all; a null window no longer aborts the decode. This release is purely the display half.
- **Not unit tested.** `UserSettings.swift` and the view helpers are not in the SwiftPM test target, so none of this logic is reachable from `swift test`. The 72 existing tests pass and cover the decode side. Extracting the active-types decision into a pure, testable function is in the backlog.

## Heads-up on update

None. No entitlements or Keychain access groups changed — the Sparkle update installs seamlessly, **no re-login required**.

## Also in this release

- `scripts/build.sh` now **fails** a Release build that cannot be notarized, instead of warning and exiting 0. Sparkle signing is gated on notarization, so the old behaviour produced a DMG that was neither notarized, stapled nor signed while reporting success — which is exactly what happened during the v1.9.4 build, when the notarytool keychain profile had gone missing. Only the unfilled appcast placeholders caught it. A missing profile, a failed notarization and a failed staple are all fatal now; `--allow-unnotarized` builds an unpublishable DMG for local testing and says so loudly. No effect on the shipped app.

## Still outstanding

Delta audit #4's larger items are not in this release. The one worth naming is the **token-rotation bug**: if you switch accounts at the moment a background token refresh completes, the new token can be written to the other account's entry, and because these tokens rotate and the old one stops working immediately, both accounts can end up signed out needing two re-authentications. Multi-account users only. Written up with exact locations in [UPSTREAM_PORT_AUDIT.md](../UPSTREAM_PORT_AUDIT.md) under "Delta audit #4".
