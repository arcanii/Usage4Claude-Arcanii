# U4Claude v1.7.0

**App Sandbox is now on.** This is the main change of the release — defense-in-depth at the OS level, a verifiable "no telemetry" claim, and alignment with what Apple has been pushing for over the last several macOS cycles.

It costs us one feature and one user-facing wrinkle on update. See **Heads-up on update** below.

## What changed

- **App Sandbox enabled.** `com.apple.security.app-sandbox` is now `true` in `Config/Usage4Claude.entitlements`, with `com.apple.security.network.client` for HTTPS to claude.ai + raw.githubusercontent.com, the existing App Group for widget data sharing, and the two `temporary-exception.mach-lookup.global-name` entries (`-spks` / `-spki`) that let Sparkle's bundled XPC services run for in-app updates. Sparkle handles its `Installer.xpc` + `Downloader.xpc` automatically via the SwiftPM integration. Also added `SUEnableInstallerLauncherService = true` to `Config/Info.plist` per the [Sparkle sandboxing guide](https://sparkle-project.org/documentation/sandboxing/).
- **"Reset Widgets" menu item retired.** The popover `…` menu no longer has the Reset Widgets button. The hard-reset tier used `Process` to `killall chronod`, which is blocked under sandbox; the medium tier alone isn't worth the menu real estate. Most widget refresh problems are now caught by the normal `WidgetCenter.shared.reloadAllTimelines()` call in `DataRefreshManager`'s success path. If chronod-cache wedges become a problem again, we'll revisit with a sandbox-compatible approach.

## Heads-up on update

Sparkle will install the v1.7.0 build into `/Applications` as usual. After it relaunches, two things may happen:

- **Re-login expected.** App Sandbox isolates Keychain items into a per-app access group. Existing v1.3.0+ users will see "Authentication not configured" on first launch — your session key is still safely in the Keychain, just not visible to the new sandboxed access group. **One-click fix: open Auth Settings → Browser Login**, sign back into claude.ai (it should remember you), and the account re-pairs in seconds. Per-account, if you had multiple.
- **Settings should carry over.** `cfprefsd` handles UserDefaults migration from `~/Library/Preferences/com.arcanii.Usage4Claude.plist` to the new container path transparently on first sandboxed launch. We log a `[SandboxBootstrap]` notice on that first launch with presence checks for the major keys so we can spot any users where the carry-over didn't take. If you see your display mode, smart-mode preference, or ring illumination reset on update, please file an issue — and reconfigure once.

## Internal

- `Config/Usage4Claude.entitlements` rewritten: sandbox-on + network.client + App Group + Sparkle XPC mach-lookup entries. The widget's entitlements file is unchanged (it was already sandbox-on).
- `Config/Info.plist`: added `SUEnableInstallerLauncherService` key. `SUEnableDownloaderService` deliberately omitted — Sparkle's guide says the Downloader service is only needed when the main app lacks `network.client`, which we have.
- `ENABLE_APP_SANDBOX` build setting flipped to `YES` for both Debug + Release configs of the main app. (Widget configs were already `YES`.)
- New first-run bootstrap block at the top of `UserSettings.init()` — logs the sandbox transition event and the presence of key UserDefaults entries so post-release reports of "settings reset" can be diagnosed from Logger output. Idempotent via a `sandboxBootstrapped_v1.7` flag.
- Deleted `Usage4Claude/Helpers/WidgetReloader.swift` (the medium + hard reset implementation) and the Reset Widgets button + comments in `UsageDetailView.swift`. Removed `L.Menu.resetWidgets` + `L.Menu.resetWidgetsHelp` from `LocalizationHelper.swift` and the `menu.reset_widgets` / `menu.reset_widgets_help` keys from all 5 locale files.
- Debug build green; 50/50 swift tests pass. Five pre-existing warnings (`UsageHistoryStore` Swift 6 concurrency + two `onChange(of:perform:)` deprecations) carry over from v1.6.x — not introduced by this release; logged for a future cleanup pass.

## What stays unchanged

- The widget extension was already sandbox-on; the main app's flip just aligns it.
- App Group sharing works identically under sandbox — verified by the existing widget integration.
- All `NSWorkspace.shared.open(url)` calls (Claude Status menu item, GitHub Sponsor, etc.) work under sandbox.
- `SMAppService` Launch-at-Login works under sandbox.
- `WKWebView` for WebLogin works under sandbox.
- Notarization, stapling, and Sparkle EdDSA signing flow are unchanged.

## Why no test rig for the v1.6.4 → v1.7.0 update path

Our user base is small and experimental; setting up a private appcast + signed test DMG just to verify cross-sandbox-state migration ahead of release isn't justified. We ship and watch the Logger output / GitHub issues. If a real problem shows up, v1.7.1 follows quickly with whatever fix is needed.
