# U4Claude v1.9.6

One fix: custom display no longer draws your 7-day limit twice.

## What changed

- **The popover circle is consistent again in custom display mode.** v1.9.5 brought the circle back for plans that no longer have a 5-hour limit, but broke custom display mode for those plans. If you use custom display with both 5-hour and 7-day ticked (the default custom selection) and "Apply only to menu bar" turned off, v1.9.5 drew the 7-day limit as both the main circle and the thin outer ring. The center read "0%" for a 5-hour limit the circle wasn't showing. The circle now shows what you ticked: an empty 0% 5-hour circle, with your 7-day limit as the outer ring.

**If your plan has no 5-hour limit and you use custom display,** untick 5-hour in Settings → General → Display Options, and the 7-day limit becomes the main circle.

Smart display mode, the default, is unchanged from v1.9.5. So is anyone whose plan still has a 5-hour limit.

## Internal

- **A correction to the v1.9.5 notes.** They said custom-mode users "still get the 0% placeholder". That was false. `toUsageData()` always produces 7-day data, so v1.9.5's fallback always found 7-day first, and its placeholder branch could never run. The claim was written from the code without checking which branch actually runs.
- The popover's ring area makes three decisions: the main circle, the thin outer 7-day ring, and whether the center shows one percentage or two stacked. They lived in three places. v1.9.5 changed how the main circle picks its limit and left the other two still asking only "are both types ticked". All three now come from one place, `Helpers/LimitDisplayLayout.swift`, so they can't disagree again.
- The main-circle design comes from upstream PR #97, by coriff, which fixes the same missing-circle bug upstream. This release adds two things #97 doesn't do. First, it keeps v1.9.5's root fix: smart mode lists the 5-hour limit only when the account has one, while upstream still lists it unconditionally. Second, the stacked center follows the outer ring's decision too. #97 changes only the outer ring, so with upstream's smart mode the center still shows a stacked "0%" for a 5-hour limit that isn't there.
- **Now unit tested.** `LimitDisplayLayout.swift` is in the SwiftPM target, which closes the gap the v1.9.5 notes flagged. There are 16 new tests (88 in total). They include the exact v1.9.5 regression, the real `five_hour: null` payload decoded through to the display decision, and an exhaustive check across every limit selection, account shape and placeholder setting. Putting v1.9.5's logic back fails 42 assertions.
- `LimitType` moved into that file so the test target can compile it. Its localized `displayName` stays in `UserSettings.swift`. Raw values are unchanged, so saved custom selections load as before.
- **Not checked on screen.** Custom mode on a plan without a 5-hour limit was verified by the tests and by reading the view code, not in the running app.

## Heads-up on update

None. No entitlements or Keychain access groups changed. The Sparkle update installs seamlessly, **no re-login required**.

## Still outstanding

Delta audit #4's larger items are still not in a release. The one worth naming is the **token-rotation bug**, which affects multi-account users only. If you switch accounts just as a background token refresh completes, the new token can be saved to the other account. Tokens rotate and the old one stops working immediately, so both accounts can end up signed out, needing two re-authentications. Written up with exact locations in [UPSTREAM_PORT_AUDIT.md](../UPSTREAM_PORT_AUDIT.md) under "Delta audit #4".
